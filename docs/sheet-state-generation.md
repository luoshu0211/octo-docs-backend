# Sheet cache generation protocol

Sheet compaction rewrites Yjs client identities. Merging a pre-compaction browser cache back into the rebuilt document can restore obsolete history and exceed the decoded-state budget. Historical version rows are separate from this limit.

## Contract

- `doc_state_generation` holds a durable generation for `doc_type = sheet`. Token issuance and document loading initialize it. It is independent of the permission epoch and does not change on ordinary edits.
- Compaction rotates the generation in the same SQL transaction as its backup and replacement state. Load reads the state and generation under the same row lock. Both synchronous and worker persistence paths reject a bound generation that no longer matches SQL, before merge/upsert.
- `stateGeneration` is returned alongside the collaboration JWT. New sheet clients use a separate IndexedDB database for each generation and disable cross-generation BroadcastChannel sharing. The provider pins that generation across JWT refreshes.
- The provider token is `{"protocol":"octo-sheet-generation-v1","token":"<JWT>","generation":"<UUID>"}`. Only the JWT authenticates and authorizes the user. Missing or stale cache generations make sheet connections read-only before the first Yjs apply. `doc.generation-stale` asks new clients to retain local state and reopen.
- The pre-sync SQL identity read must not outlive its authorization decision: if the local permission watermark advances while SQL is pending, recheck the actor and read the identity again before applying the message. Role reads, their cache and singleflight are permission-epoch-bound; a further invalidation during a role read forces another recheck. Lookup failures reject the message. Capacity/generation read-only state is never cleared by a successful permission refresh.
- Redis document channels and store locks are generation-specific. The adapter also discards queued messages from a former subscription. Its private `getKey`/`handleIncomingMessage` seam targets the pinned Hocuspocus Redis 4.4.0 implementation; revalidate two-node loading, pub/sub, stateless receipts and unload on dependency upgrades.
- `doc.persisted` contains the generation and a base64 encoded Yjs snapshot captured with the saved update, emitted only after COMMIT. It contains both clocks and deletion ranges: clocks alone cannot acknowledge delete-only edits. Later live edits are not covered by an earlier receipt. Receipt delivery failure does not undo a successful store.
- Nodes retain valid same-generation peer receipts for replay to later connections, including receipts received during document loading. Local and peer receipts merge monotonically (maximum clocks and unioned deletion intervals). The wire codec is `Y.encodeSnapshot`/`Y.decodeSnapshot`, not the V2 snapshot codec. Never derive peer coverage from the receiving node's live state, which may contain unsaved edits.
- Sender, peer retention, and frontend consumption accept the same committed snapshot sizes. Do not add a receiver-only character limit: many retained CRDT identities can produce a receipt above two million characters for a document below the decoded-state budget. Peer receipt validation still requires the correct generation, canonical base64 and canonical snapshot bytes. The document storage limit is unchanged.
- Generation-aware sheet close/saved status waits for a receipt covering the current snapshot. The browser retains old caches, offers a full Yjs backup and can rebuild current flat sheet values with new identities into a separate authorized document. A copy is reported saved only after its own commit receipt. Unsupported nested shared values fail recovery explicitly. Linked files remain references; no automatic business-level merge or attachment duplication is performed.

## Deployment and rollback

1. Apply `migrations/upgrades/2026-10-10-sheet-state-generation.sql` before starting the new backend. It is idempotent. Ensure all existing sheet rows have a generation, including rows whose legacy `compactedAt` stamp is suppressed by an unresolved over-cap marker.
2. Deploy the paired frontend. It can still talk to a legacy server; generation isolation becomes active when the server returns the new field.
3. Drain and replace every old backend writer together. Do not run mixed legacy/new backend writers against the same sheets: old binaries lack the SQL generation fence and use the old Redis channel. Restarting only one node does not clear another node's polluted memory. Preserve authoritative SQL snapshots and browser recovery sources before maintenance.
4. Open a fresh sheet client, then test a retained old cache, an old frontend, normal edit/delete, two-node propagation, reconnect, and copy recovery. Old frontends become read-only and must refresh. Only the completed fleet transition enforces the invariant.
5. Roll back with another coordinated drain, retaining the generation table and recovery caches. A legacy backend re-enables the old cache-reflow behavior; do not call it a safe partial rollback. Existing gzip/encoding compatibility and decoded/storage limits remain independent rollout requirements.

The change prevents cross-generation reflow. It does not shrink an already oversized authoritative row, raise limits, or prove which exact packet caused a historical production incident. Rebuilt copies can also exceed limits when their current values are themselves too large; failure retains the source and may leave a new draft in the list.

## Verification

Unit coverage includes transaction ordering/refusal, stale SQL writers in both storage modes, failure before COMMIT, edits arriving while saves await, delete-only receipts, identity-preserving token refresh, isolated cache discovery and retained recovery values. Mutation checks remove the SQL fence or delete coverage and must fail before restoration.

Redis receipt regressions exercise the pinned extension's binary message dispatch, retention before Hocuspocus registration, independent/out-of-order commits, multi-item deletion intervals, invalid frames, and unload/reload isolation. The frontend constructor tests exercise real Yjs/IndexedDB with transport/rendering doubles, including legacy-server fallback; removing each of the eight cache/connection/editability/teardown guards must fail. A two-node real SQL/Redis probe pauses B's local saves, commits on A, then opens a later connection on B and separately checks that B's uncommitted live edit remains unacknowledged.

Valid large-receipt regressions build 375,256 distinct three-byte client IDs, encode the actual document below 10 MiB, then pass its canonical snapshot through peer retention and the frontend controller's stateless handler. The default suite also invokes the real server `connected` hook after a peer commit, checking replayed deletion coverage and exclusion of later unsaved edits. Restoring either peer size cap, restoring the frontend cap, or removing connect-time receipt delivery must fail its corresponding regression.

Pre-sync regressions drive the real Hocuspocus Connection queue, configured hook dispatcher and MessageReceiver with controlled SQL/role reads. Revoke during the identity await and again during a role await; assert unchanged Yjs bytes and no update event, not only readOnly. Also cover SyncStep2, cached/in-flight roles from older epochs, valid writers, generation rotation and lookup failure. Benchmark writers load their state and generation together through persistence.fetch, including on reruns and for each concurrency participant.

An inherited operational limitation remains outside this change: a failed store can retain a dirty document without an automatic retry and leave graceful shutdown waiting for unload. Commit receipts do not claim success for that state; bounded retry/shutdown handling needs a separate change.

Local two-node verification uses the copied 4,493,001-byte incident row plus the old/synthetic cache fixture. Missing/stale generations leave both live nodes and SQL at 4,493,001 bytes; normal writes and same-generation offline edits still persist. A separate forced overlap validates old-channel, old-socket and old-SQL-write fencing; actual unloaded compaction validates atomic generation rotation. Real authenticated browser verification creates the source via the product, edits offline across a simulated generation boundary, downloads the retained cache, saves a new sheet and checks it after reopening. These are local results, not a production deployment claim.
