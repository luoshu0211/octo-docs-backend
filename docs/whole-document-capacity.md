# 全量文档内存改造与容量验证（2026-10-16）

**结论：这轮降低了内存并补上了部分保护，但没有消除所有 OOM 路径。当前不能直接提高全局 10 MiB / 100 万格限制。20 MiB 可以进入下一轮受控验证；32 MiB 不能当作安全上限；100 MiB 暂不支持按现有方式开放。**

以下容量数据来自 2026-10-16 的 `feat/whole-doc-capacity-20261016`，测量基线为后端 test 提交 `2bce77be9ec80233fde981a2b495185dd2bf59a6`。2026-10-19 的交付分支 `perf/yjs-memory-20261019` 基于更新后的 test 提交 `08b446875e7678003e62d4052af7573b527909ed`；交付复核另列于文末，不将旧压测表述为新基线重测。尚未部署。这轮保留全量 Y.Doc 模型，没有扩大分块原型范围，也没有修改现行容量配置。

## 已实现的修改

1. **减少每格的常驻对象开销。** Yjs 解码单个值原先用空数组逐项 push，V8 会为它预留多余空间。现在单值直接构造 `[value]`，在本轮 Node 22 实测中每格减少约 128 字节。固定 Yjs 13.6.31，在安装时校验并修改 source / ESM / CJS 三个入口；不改变数据格式。V1/V2 原版样本逐字节往返、并发修改、删除和撤销均通过。
2. **让保存进程的内存限制真正生效。** 原 worker_threads 的 512 MiB 配置会被父进程的 NODE_OPTIONS 覆盖，实测会变成约 4 GiB。保存改用独立进程，显式设置 512 MiB old-space，并检查实际 V8 堆上限。失败后等待进程真正退出才释放任务位置和字节预算，避免新旧解码任务同时占内存。512 MiB 不包含全部 RSS、Buffer 和父进程内存。
3. **把排队放在昂贵操作前。** 保存先取得执行资格，再编码快照、取 SQL 行锁；执行队列最多接收 16 个任务，串行执行。队列满或排队超过 30 秒时，已接受编辑的保存流程保持等待，收到任务完成信号后重新申请资格，不提前返回成功或卸载文档。等待期间不编码快照、不取 SQL 锁，也不轮询。新文档加载仍用可拒绝的串行队列，最多接收 32 个任务。保存等待者保留原文档引用，因此执行队列有界不等于驻留文档总数或请求耗时有界。
4. **新文档加载检查内存余量。** 检查主进程堆水位，以及容器存在明确限制时的剩余内存；给保存进程、缓冲区和正在加载的数据留空间。拒绝过载的新加载，不把用户现有编辑强制丢弃。这个水位检查不能预测任意下一份文档的解码成本，下面的 OOM 反例证明它仍不是完整保证。

## 单文档对照

环境：同一 Linux ARM64 / Node 22.23.2，2 CPU、4 GiB 容器、父进程 old-space 4 GiB；同一份确定性 Yjs V2 数值表文件；每档改前/改后各 3 次。内容为 `sheet` map，键为 `default!行:列`，值为 `{v:数字,t:2}`。MiB 指 **Yjs 序列化大小**，不是 XLSX 压缩包大小。

“保留堆”为加载后显式 GC 的中位数；“容器峰值”为三次完整执行中的最大值，包括加载、准备保存、辅助进程和结果校验。它不是纯保存阶段峰值，更不是完整产品节点的预算。固定文件在另一个进程生成；校验会额外编码，因此这里不据其耗时宣称生产保存延迟改善。

| Yjs 大小 | 实际有值单元格 | 保留堆：改前 → 改后 | 容器峰值：改前 → 改后 | 改后保存 |
|---|---:|---:|---:|---|
| 10.23 MiB | 32 万 | 168 → 129 MiB | 622 → 537 MiB | 3/3 成功 |
| 20.25 MiB | 63 万 | 326 → 249 MiB | 1,093 → 941 MiB | 3/3 成功 |
| 32.22 MiB | 100 万 | 498 → 376 MiB | 1,578 → 1,308 MiB | 3/3 成功 |
| 49.29 MiB | 150 万 | 758 → 575 MiB | 2,336 → 1,459 MiB | 0/3，保存进程超预算退出 |

49.29 MiB 的改后峰值较低，是因为任务被中断，**不能当作成功保存后的节省**。后续小文档保存成功，但失败的大文档没有持久化。

另测 104.29 MiB / 3,106,503 格：

- 改前：加载后的保留堆约 1.53 GiB，RSS 约 1.93 GiB；保存时整个 4 GiB 容器 OOMKilled，退出 137。
- 改后：保留堆约 1.16 GiB，RSS 约 1.55 GiB，堆下降约 24%；保存辅助进程堆耗尽，主进程存活，整轮容器峰值约 2.43 GiB，随后小文档保存成功。
- **这证明故障隔离改善，不证明 100 MiB 保存可用。**

## 多文档与真实持久化

最终版本的加载水位在 **2 GiB / old-space 1,536 MiB / 2 CPU** 容器中，连续尝试加载不同文档，然后保存已有文档。加载过程中不强制 GC：

| 每篇文件 | 结果 | 整轮容器峰值 | 判断 |
|---|---|---:|---|
| 10.23 MiB | 接收 7 篇，拒绝下一篇；已有文档及后续小文档保存成功 | 1,297 MiB | 这个样本的保护有效；拒绝后不能算 100 篇成功 |
| 20.25 MiB | 接收 4 篇，拒绝下一篇；保存成功 | 1,740 MiB | 余量有限，不能直接搬成生产并发配额 |
| 32.22 MiB | 接收 3 篇后，保存时容器 OOMKilled / 137 | 达到容器限制 | **单篇通过，组合仍失败** |

早期较小的预留空间曾让 5 篇 20.25 MiB 文档把容器推到约 94% 内存；因此已提高预留。最终的 32 MiB 反例仍说明：只看当前水位不足以涵盖“下一篇展开 + 后续保存”的峰值。继续提高水位预留会减少可用容量，不能替代按文档估算并预留资源。

另外用两个独立 Node 22.23.1 进程、实际 Hocuspocus、专用 MySQL / Redis，验证同一份 20.25 MiB 表：

- 100 次交替修改、同时写不同单元格、删除、保存、断开后重新加载，结果一致。
- 保存进程失败时，SQL 旧内容校验和不变；没有新“已保存”回执；未保存编辑仍留在服务端文档中；另一个进程可以继续保存。
- 该脚本是直连协作核心的真实存储验证，**没有产品身份认证和浏览器**。它使用依次等待同步的闭环工作负载：目标 20 次/秒，实际约 8.42 次/秒，P95 约 190 ms。因此没有获得“持续 20 次/秒”的吞吐资格，也不能推导 1,000 / 10,000 用户容量。

## 如何调整上限

| 项目 | 当前决策 | 理由与放行条件 |
|---|---|---|
| 全局文档上限 | 保持 10 MiB | 整体 OOM 尚未闭合；单篇通过不代表整个节点安全 |
| 20 MiB | 下一轮候选，暂不全局开放 | 单篇和有限驻留样本通过；还需真实产品基线、按文档预留、开放式并发压测、浏览器/导入验收 |
| 32 MiB | 不作为安全上限 | 2 GiB 节点三篇驻留后保存已有明确 OOM 证据 |
| 100 MiB | 当前路径不能开放 | 新保存进程超预算；每篇全量模型仍超过 1 GiB；浏览器未改造/验证 |
| 100 万格 → 更大 | 保持现状 | 100 万实值格已是约 32 MiB；网格行列乘积、实际有值格数和内存不是同一指标，前端模型/公式尚未验证 |

下一步应先完成：**在加载前按文档成本预留整个节点的空间，保存也申请独立预算，并覆盖 WebSocket、CLI/REST、导入和导出入口**。失败的保存需要完整的编辑暂停与恢复交互；本轮仅对保存队列的满载和超时保持等待，避免这两类拥堵导致假成功，不能据此推断所有 SQL、辅助进程或存储预算失败都已安全处理。等待中的原文档仍占内存，长期拥堵也会延长请求耗时。然后使用真实产品的基本内存占用、样式/公式/长文本/历史数据以及固定速率并发，验证候选 20 MiB。

如果必须支持 100 MiB，需继续降低保存完整快照的临时成本（例如经过正确性验证的增量持久化、受控检查点），并解决浏览器全量模型的成本；必要时再做服务端和浏览器按需加载。加一个节点、改成磁盘文件或单独提高 worker 堆，都不能自动消除上述峰值。

## 保存拥堵的 CR 修复（2026-10-20）

审查针对 `42b98eabcbcb2f37f905af26bd5608b73846b4cb` 指出：Hocuspocus 的 `storeDocumentHooks` 会捕获保存失败并返回，随后直接连接的 `disconnect()` 仍可能卸载零连接文档。新增队列的拒绝因此会让普通小文档的 REST 编辑返回成功，却没有落盘。

- 独立复现使用真实 Hocuspocus、CollabDatabase、persistence 和保存子进程，仅模拟 SQL 事务及通知旁路。阻塞第一个保存，分别制造 16 个任务满载和 30 秒排队超时；同步与后台保存的 4 种组合均在原实现上失败。
- 保存入口改用 `runRetained`：只对**操作尚未开始**的排队拒绝等待任务完成信号，再重新申请资格。等待时 Hocuspocus 继续持有保存互斥锁，直接连接的断开不提前完成，也不会走到卸载。执行中的操作仍然串行；SQL、解码、大小限制等操作内部异常原样向上传递，不自动重放。
- 回归覆盖：拥堵时文档仍存活且没有额外 SQL 读取；另一直接连接在等待期间修改、删除后，保存读到最新内容；放开队列但阻塞 COMMIT 时仍不返回；提交后卸载、重新加载，内容一致。
- 只把保存入口改回旧的 `run`，4 个断开连接回归全部失败；恢复后通过。另验证活动任务失败仍能唤醒等待者、等待不轮询、已开始执行的错误不会被自动重试。
- macOS / Node 22.23.1：3 个相关文件 41 项通过、0 跳过；全量 311 个文件，4,547 项通过、58 项跳过、0 失败；类型检查、编译及改动文件 ESLint 通过。
- 这不是新的容量压测、真实数据库/Redis或浏览器验收，不改变文档及单元格上限。长期存储拥堵仍保留未保存的原文档并延长请求耗时，不能当作完整的 OOM 或宕机持久性保证。
